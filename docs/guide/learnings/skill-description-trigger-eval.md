# SKILL.md description 축소의 트리거 회귀 실측

## Context

이슈 #1417 (#1411 의 미충족 수용 기준 승계), 관련 #1410 · #1412.

#1411 이 71개 `SKILL.md` 의 `description` 을 47,449 → 16,852자 (-64.5%) 로
줄였다. 축소의 유일한 실질 리스크는 **길이는 통과하는데 트리거가 안 걸리는**
상태인데, `skill:check` Check 16 은 길이만 재므로 그 상태를 그대로 통과시킨다.
본 문서는 그 갭을 실측으로 메운 결과와, 측정하면서 드러난 하네스 함정을 남긴다.

산출물:

- `claude/skills/<skill>/evals/trigger-eval.json` — 표본 16종 × 20쿼리
- `claude/tools/run-trigger-eval.sh` — 격리 하네스 (수동, API 예산 소모)
- `claude/skills/skill-check/references/trigger-eval-procedure.md` — 절차 SSOT
- `tests/integration/test_trigger_eval_sets.py` — 세트 불변식 CI 가드

## Pattern

### 1. 측정 도구가 조용히 0점을 내는 4가지 경로

`run_eval.py` 는 평가 대상 description 을 uuid 이름의 임시 슬래시 커맨드로
등록하고 `claude -p` 가 **그 이름**을 부르는지 본다. 같은 스킬의 쌍둥이가 하나라도
더 보이면 모델이 그쪽을 부르고 프로브의 uuid 는 끝내 등장하지 않아 **정상 트리거가
미스로 기록된다.** 에러는 나지 않는다.

| # | 쌍둥이 출처 | 격리 | 실측 근거 |
|---|---|---|---|
| 1 | 설치된 스킬 (`~/.claude*/skills/` 71종) | `CLAUDE_CONFIG_DIR` 를 credentials 만 든 임시 dir 로 | #1412: 노출 154 → `0.0`, 노출 50 → `1.0` |
| 2 | 이전 실행이 남긴 프로브 | 잡마다 새 프로브 프로젝트, 종료 시 삭제 | #1412 |
| 3 | **동시 실행 프로브** | `run_eval --num-workers 1` 고정 + 병렬화를 `--jobs` 로 한 단계 올림 | #1417: 동일 쿼리, `b41dae08` **이전** `--num-workers 3` → **0/3 FAIL** vs `1` → **3/3 PASS**; **이후** 재측정 **1/3 FAIL** vs **3/3 PASS** |
| 4 | 실제 체크아웃 | `PYTHONPATH` 지정 + cwd 를 프로브 프로젝트로 | 2번의 변종 |

3번이 이 이슈에서 새로 찾은 함정이다. **하네스가 스스로 만드는 쌍둥이**라
"빠르게 하려고 워커를 늘리는" 자연스러운 최적화가 측정을 조용히 망가뜨린다.

### 그 사이 #1412 가 고쳐졌다 — 그리고 그게 결론을 바꾼다

본 작업 도중 `b41dae08` 이 main 에 들어와 #1412 의 세 결함을 모두 고쳤다:
첫 툴 블록 조기 판정이 사라져 `TriggerDetector` 가 스트림 전체를 보고, 에러 런이
분모에서 빠진다 (`claude/skills/skill-create/references/local-patches.md`).

**고쳐진 뒤 두 핀을 각각 재측정했고, 결과가 갈렸다:**

| 핀 | `b41dae08` 이전 근거 | 이후 재측정 | 판정 |
|---|---|---|---|
| `--num-workers 1` | 3 워커 0/3 vs 1 워커 3/3 | 3 워커 **1/3** vs 1 워커 **3/3** | **여전히 필요** |
| `--model sonnet` | opus 0/2 vs sonnet 1/1 | opus **3/3**, sonnet **3/3** | **정확성 근거 소멸** — 비용 이점만 남음 |

이게 이 문서에서 가장 재사용 가치가 큰 교훈이다: **결함을 근거로 세운 핀은 그
결함이 고쳐지면 반드시 재측정해야 한다.** 안 그러면 근거가 조용히 미신이 된다.
"3번은 하네스 자신이 만드는 쌍둥이라 상류 수정과 무관하다"는 추론은 맞았지만,
맞았다는 것도 재측정해서야 알았다.

판별 신호: 전체 점수가 50% 근처인데 **recall 0/10 · reject 10/10**. 모든 쿼리가
"미트리거"로 채점되면 reject 클래스는 만점이 되어 그럴듯한 점수로 보인다.
`run-trigger-eval.sh` 가 recall/reject 를 분리 출력하는 이유다 — 진짜 측정은
recall 이 0 이 아니다.

### 2. 트리거 검출은 모델에 따라 달랐다 — 그리고 지금은 아니다

`b41dae08` **이전** `run_eval.py` 는 **첫** `content_block_start` 의 도구가
`Skill`/`Read` 가 아니면 즉시 `False` 를 돌렸다. 동일 쿼리 실측:

| model | 이전 | `b41dae08` 이후 |
|---|---|---|
| `opus` | **0/2 FAIL** (실제로는 `Skill` 호출이 일어났으나 검출기가 놓침) | **3/3 PASS** |
| `sonnet` | **1/1 PASS** | **3/3 PASS** |

계약이 두 description 사이의 **델타**라 모델은 최대화 대상이 아니라 **양쪽 arm 에서
고정**되기만 하면 된다. 그래서 여전히 `sonnet` 을 기본값으로 두지만, 이유는 이제
"검출기가 읽을 수 있는 유일한 티어"가 아니라 **동일 진단력에 비용이 한 자릿수 싸다**
뿐이다. `description-optimization.md` 의 "세션 모델을 쓰라"는 지침은 description 을
**최적화**할 때의 것이고, 여기서는 고정이 목적이라 여전히 그대로 적용하지 않는다.

**본 측정치는 전부 `b41dae08` 이전 러너로 얻었다.** 양쪽 arm 이 같은 러너를 썼고
계약이 델타라 내부적으로는 유효하지만, **오늘의 `run_eval.py` 로는 재현되지 않는다**
(고친 러너가 트리거를 더 많이 잡는다). 새 수치를 이 표와 비교하려면 먼저 재측정하고,
어느 러너에서 나온 숫자인지 항상 함께 적는다.

**첫-행동 제약은 남는다.** 조기 판정은 사라졌지만 프로브는 여전히 자기 uuid 를
불러야 트리거로 잡히므로, should-trigger 쿼리는 **스킬 참조가 자연스러운 첫 행동**이
되게 쓴다. "파일 찾아서 …", "테스트 돌려보고 …" 처럼 다른 도구를 먼저 부르게 하는
문장은 측정을 흐린다. 실측 사례: 슬래시 리터럴만 던지는
`/devx-pr-verify-merged 1388 --matrix full` 류 쿼리는 **description 이 그 alias 를
광고하든 안 하든 전 arm 0/3** 이었다 — `-live`(alias 있음)와 `-merged`(없음)가
동일하게 0/3 이라 alias 유무가 원인이 아님이 대조로 확인된다.

### 3. 세트를 비교 가능하게 만드는 불변식

- **10/10 고정 분할** — 점수가 곧 백분율이 되어 5%p 계약이 의미를 갖는다.
- **양방향 교차** — 경쟁 쌍은 상대의 should-trigger 를 자기 should-NOT-trigger 로
  넣는다. 한 방향만 걸면 더 비싼 오발화가 미측정으로 남는다.
- **자연어 우위** — #1410 이 네임스페이스를 전부 바꾸므로 슬래시 리터럴 쿼리는
  무효화된다. 자연어 쿼리가 리네임 전후를 잇는 고정점이고, 리터럴 쿼리에는
  `note` 로 갱신 대상 표시를 남긴다.
- **양쪽 description 어느 쪽 문구도 베끼지 않는다** — 옛 문구를 베끼면 before 로,
  새 문구를 베끼면 after 로 결과가 기운다. 쿼리는 SKILL.md **본문**(스킬이 실제로
  하는 일)에서 사용자 어휘로 쓴다.

이 불변식들은 `tests/integration/test_trigger_eval_sets.py` 가 CI 에서 고정한다.

### 4. 노이즈 바닥이 계약 마진과 같다

세트가 20쿼리라 **쿼리 하나가 뒤집히면 5%p** — 계약 마진과 동일한 크기다.
±5%p 안쪽의 델타는 "개선/퇴행"이 아니라 **"변화 미검출"** 로 읽어야 한다.

## Code

```bash
# 표본 전체, 양쪽 arm
claude/tools/run-trigger-eval.sh gh-commit gh-pr sh-check

# 음성 대조군 — 트리거 문구를 제거한 변형이 실제로 점수를 떨어뜨리는지
claude/tools/run-trigger-eval.sh --description "$(cat gutted.txt)" sh-check
```

`--num-workers` 는 일부러 노출하지 않는다 (위 함정 3).

**올랐다.** 축소가 곁가지를 걷어내 경계가 더 또렷해진 경우다. 다이어트 자체가
문제가 아니라, **경계 문장을 지웠는지**가 문제다.

### 미달 2건 처리 — 부정 트리거와 긍정 판별자는 서로 다른 절반을 고친다

#1411 결정 D-1 의 예외 규칙(미달 건은 WARN 251~400 으로 되돌리고 근거 주석)을
적용하되, **되돌린 문안이 실제로 계약을 회복하는지 매번 재측정**했다. 그 과정에서
두 스킬이 서로 다른 것을 잃었다는 게 드러났다.

`devx-pr-verify-live` — 경계 문장 하나만 복원:

| arm | score | recall | reject | 길이 |
|---|---|---|---|---|
| before | 85% | 8/10 | 9/10 | 954 |
| after (#1411) | 65% | 8/10 | **5/10** | 240 |
| **복원** | **90%** | 8/10 | **10/10** | 379 (WARN) |

`devx-pr-verify-merged` — 두 조각을 나눠 측정:

| arm | score | recall | reject | 길이 |
|---|---|---|---|---|
| before | 90% | 8/10 | 10/10 | 882 |
| after (#1411) | 75% | 7/10 | 8/10 | 244 |
| 경계 문장만 복원 | 75% | **5/10** | 10/10 | 374 |
| **경계 + 긍정 판별자 복원** | **90%** | **8/10** | **10/10** | 388 (WARN) |

읽어낼 규칙: **부정 트리거(`Do NOT use ... — that is X`)는 reject 를 고치고,
긍정 판별자("no running app", "dirty worktree" 같은 언제-쓰는가 조건)는 recall 을
고친다.** `live` 는 경계만 잃어서 경계만 돌려주면 됐고, `merged` 는 둘 다 잃어서
경계만 돌려주면 오발화는 멈추지만 자기 쿼리를 놓쳤다.

두 건 모두 WARN 밴드(251~400)에 착지했고 근거는 frontmatter 주석으로 남겼다 —
`skill_desc_extract` 가 `description:` 앞의 YAML 주석을 세지 않으므로 근거를
값 바로 옆에 두면서도 측정 길이는 오염되지 않는다. 전체 총량은 16,852 → 17,131자
(#1411 의 18,000자 목표 이내), 71종 기준 PASS 69 / WARN 2 / FAIL 0.

**남은 잔여 누수 (숨기지 않고 기록).** `devx-pr-verify-merged` 의 교차 쿼리 5건
중 2건은 완전히 0 으로 돌아오지 않았다:

| arm | 교차 5건의 trigger rate |
|---|---|
| before (pre-#1411) | `[0, 0, 0, 0, 0]` |
| after (#1411) | `[0, 0, 0, 3, 3]` |
| 복원 (본 작업) | `[0, 0, 0, 1, 1]` |

즉 **결정적 오발화(3/3)가 임계 아래 플레이크(1/3)로 내려왔을 뿐** 다이어트 이전의
0/3 을 완전히 회복하진 못했다. `run_eval` 의 판정 임계가 0.5 라 1/3 은 "미발동"으로
채점되고 따라서 reject 10/10 · 계약 PASS 는 정당하지만, "상대 쿼리에 절대 발동하지
않는다"를 문자 그대로 주장할 수는 없다. 두 쿼리 모두 "앱이 이미 떠 있는데 그게 이
머지 커밋을 서빙하는지" 계열이라 판별 축이 정확히 맞물리는 지점이다 — 재측정 폭
15%p 를 감안하면 1/3 은 노이즈 범위이기도 하다. 더 줄이려면 `merged` 쪽에 "이미
떠 있는 앱" 을 명시적으로 배제하는 문장을 추가해야 하는데, 후보 1에서 그 문안이
recall 을 8/10 → 5/10 으로 떨어뜨렸다. **reject 를 마지막 1/3 까지 짜내는 대신
recall 을 지키는 쪽**을 택했고, 이 트레이드오프는 후속 관찰 대상으로 남긴다.

### 음성 대조군 — 도구가 진짜 회귀를 잡는가

`devx-mise-migrate` 의 10개 should-trigger 쿼리에 세 가지 description 을 물렸다.

| description | recall | score |
|---|---|---|
| 실제 (post-#1411) | 7/10 | 85% |
| **키워드 제거, 의미 보존** | 7/10 | 80% |
| **완전 무관 도메인** | **0/10** | 50% |

가운데 행이 핵심이다. `mise` · `uv` · `venv` · `pip` · `Python` · 슬래시 리터럴 ·
한국어 트리거 문구를 **전부** 지우고 "toolchain versions, environment variables,
and command entry points in a single declarative manifest" 라는 패러프레이즈만
남겼는데 **트리거가 전혀 흔들리지 않았다.**

즉 **매칭은 의미 기반이지 문자열 기반이 아니다.** 두 가지 결론:

1. 도구의 유효성은 3행이 증명한다 (0/10 으로 붕괴). 음성 대조군은 **의미를**
   깨야 한다 — 키워드만 지우고 같은 일을 패러프레이즈하면 대조군이 아니다.
2. 이것이 #1411 의 다이어트가 대체로 안전했던 메커니즘이다. 지운 것은 인용된
   트리거 문구와 옵션 산문이고, 남긴 것은 "이 스킬이 무엇을 하는가" 문장이다.
   트리거는 그 문장 위에서 돈다.

### 재현성 — 계약 마진과 노이즈가 같은 크기다

세트가 20쿼리라 **쿼리 하나 = 5%p**, 계약 마진과 동일하다. 동일 description ·
동일 세트로 `sh-check` after 를 세 번 재면:

| 회차 | score | recall |
|---|---|---|
| 1 | 70% | 4/10 |
| 2 | 85% | 7/10 |
| 3 | 80% | 6/10 |

**같은 arm 의 재측정 폭이 15%p** — 계약 마진의 3배다. 따라서 **±5%p 안쪽 델타는
"변화 미검출"로 읽어야 하고**, 표의 PASS 대부분(±5%p)은 "회귀 없음"이지 "개선"이
아니다. 단일 측정으로 스킬 하나를 판정하지 말 것.

행동으로 옮길 만한 신호는 (a) 크기가 노이즈를 크게 넘고, (b) recall/reject 중
어디가 무너졌는지 설명되며, (c) 원인 문장을 지목할 수 있을 때다. 미달 2건은
셋을 모두 만족한다.

`gh-commit before` 의 `recall 0/10` 은 별도로 유의할 점이다 — 커밋은 Claude 가
스킬 없이도 그냥 할 수 있는 일이라 첫 도구가 `Bash` 가 되고, 그러면 하네스가
"미트리거"로 채점한다. 저빈도 recall 은 description 품질이 아니라 **작업 자체의
자명함**을 반영할 수 있다.
