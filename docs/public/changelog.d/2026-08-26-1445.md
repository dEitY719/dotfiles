- 변경: **`gh:issue-create` 의 `addBlockedBy` 인자 형태를 검사 2건으로 고정한다 (issue #1457).** #1445 가 고친 드리프트(`blockedByIds` → `blockingIssueId`)에 대해 `tests/bats/skills/gh_issue_create_dependency_detect.bats` 는 수정 전후 트리에서 똑같이 23/23 초록이었다 — 즉 그 스위트는 해당 수정을 아무것도 증명하지 못했다(PR #1450 을 머지 커밋의 신선한 클론에서 차등 검증하다 실측). 이제 두 검사가 서로 다른 실패를 잡는다. (1) **오프라인** — `references/dependency-detect.md` 의 mutation 문자열이 여전히 `blockingIssueId` 를 쓰는지, 그리고 드리프트된 배열 철자가 파일 어디에도 없는지 단언한다. 네트워크 없이 돌므로 최소 방어선이 항상 남는다. (2) **라이브 스키마** — `AddBlockedByInput` 의 입력 필드를 introspection 으로 실 API 에 물어 `blockingIssueId,clientMutationId,issueId` 와 대조한다. 이건 목이 아니라 읽기 전용 질의이므로 #1445 확정 3("`gh` 를 목으로 대체하지 않는다")에 걸리지 않는다. `gh auth status` 실패나 질의 실패 시 **skip** 으로 끝난다 — 오프라인 셸에서 무관한 빨강을 만들면 검사 자체가 꺼지고, 네트워크 있는 실행 한 번이면 드리프트는 잡히기 때문이다. bats 의 `setup_isolated_home` 이 `$HOME`/`$XDG_CONFIG_HOME` 을 샌드박스로 바꾸므로 `gh` 가 항상 미인증으로 보여 영구 skip 이 될 뻔했다 — 파일 로드 시점(즉 `setup()` 이전)에 실제 설정 위치를 붙잡아 읽기 전용으로만 복원한다. 검증: 문서를 `blockedByIds` 로 되돌리면 (1)이 빨강이 되고 나머지 24건은 초록으로 남는 차등을 실측 확인했다 — 이 차등이 성립하지 않는 것이 이슈의 존재 이유였다. 스킬이 실제로 보내는 mutation 은 그대로이고, 범위는 `addBlockedBy` 하나다(읽기 경로 `Issue.blockedBy` 는 #1445 에서 정상 확인).
