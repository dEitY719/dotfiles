- 변경: **`gh:commit` 과 `gh:pr` 이 `[remote]` positional 을 받는다 — `/gh:commit [issue-number] [remote]`, `/gh:pr [N] [remote] [--no-stack] [--base <branch>]` (숫자만인 positional 은 이슈 번호, 그 외는 remote 이름; 기본값 `origin`). 그리고 `gh:issue-flow` 가 자신의 `[remote]` 를 Step 2.2/2.3 의 `Skill()` 호출에 실제로 넘긴다. 종전에는 `gh:issue-flow` Step 1 이 `[remote]` 로부터 `TARGET_REPO`/`TARGET_HOST`/`GH_HOST` 를 바인딩해도 Step 2.2(`gh:commit`)와 Step 2.3(`gh:pr`)이 각자 `origin` 에서 다시 해석했고 `gh:pr` 은 `[remote]` 인자를 받지도 않았다 — 그래서 `/gh-issue-flow <N> upstream` 이 커밋의 ai-metrics 코멘트와 PR 자체를 `upstream` 이 아니라 `origin` 에 올렸다(#1403 리뷰에서 codex 가 지적, PR #1404 범위 밖이라 별도 추적). Claude Code 는 tool call 마다 셸이 분리되어 export 한 변수가 `Skill()` 경계를 넘지 못하므로, 환경 상속이 아니라 인자 전달 방식을 택했다. `gh:pr` 에서는 remote 가 GitHub API 대상(host + `--repo`)뿐 아니라 git plumbing 까지 함께 좌우한다 — `git fetch <remote>`, `<remote>/$BASE_BRANCH` 범위 비교, upstream 페어링 판정, `git push -u <remote> HEAD`. 이에 맞춰 SSOT 함수 `gh_pr_upstream_is_mispaired` / `gh_pr_push_action` / `find_parent_pr_candidates` 가 `origin` 기본값을 갖는 후행 remote 인자를 받도록 확장됐고(기존 호출과 기대값은 그대로), 미러 fixture `tests/bats/skills/_fixtures/gh_pr_push_policy.sh` 와 `gh_pr_stacked_detect.sh` 도 lockstep 으로 갱신됐다. 존재하지 않는 remote 를 넘기면 `git remote -v` 목록과 함께 정지한다 — 조용한 `origin` fallback 은 오타를 가려 엉뚱한 repo 에 쓰기 때문에 금지 (#1405)**
- 변경: **공용 헬퍼 `shell-common/functions/gh_project_status.sh` 가 대상 repo 를 명시적으로 받는다 — `_gh_project_status_sync ... [--repo <owner/repo>]`, `_gh_project_status_query_current <kind> <num> [<owner/repo>]`. 해석 우선순위는 `--repo` 인자 > `$GH_REPO` > `$TARGET_REPO` > `gh repo view` 자동 탐지. 종전에는 `_gh_project_status_ensure_host` 로 host 만 고정(#804)하고 repo 는 무조건 `gh repo view --json owner,name` 으로 해석했는데, `--repo` 없는 `gh repo view` 는 git 의 `origin` 이 아니라 gh CLI 자신의 `gh repo set-default` 를 답하므로 한 host 에 여러 remote/repo 가 걸린 작업 트리에서 **다른 repo 의 보드를 동기화**할 수 있었다(#1403 리뷰에서 agy 가 지적). 새 `_gh_project_status_normalize_repo` 가 `OWNER/REPO` 와 `HOST/OWNER/REPO` 두 형태를 받고, **명시적으로 준 값이 malformed 면 fail-closed(rc 1)** — 오타가 자동 탐지로 되살아나 엉뚱한 보드를 건드리는 일을 막는다. 반면 **빈 문자열은 "미지정"** 으로 취급해 다음 우선순위로 흘려보낸다(호출자가 `--repo "$SOME_VAR"` 를 넘기는데 그 변수가 일시적으로 비는 경우 전체 sync 를 통째로 건너뛰지 않도록 — #341 재시도를 무력화하지 않기 위함). 부수 변경 두 가지: (1) `Approved` fail-closed 게이트의 `gh pr view` 도 이제 `--repo` 를 달고 나가며, 그러기 위해 repo 해석 블록을 게이트 **앞** 으로 옮기되 해석 실패가 게이트를 건너뛰지 않도록(fail-closed 가 fail-open 으로 바뀌지 않도록) bail-out 을 게이트 뒤로 미뤘다. (2) 내부 `_gh_project_status_set_and_verify` 가 verify 재조회에도 같은 repo 를 물려받는다 — 그러지 않으면 mutation 은 pin 된 repo 로, verify 는 자동 탐지 repo 로 나뉘어 정상 동작이 "verify failed twice" 로 오보고된다. 호출자 일괄 점검 결과 `gh:pr-approve` / `gh:pr-merge` / `gh:pr-merge-emergency` / `gh:pr-reply` / `gh:pr-resolve-conflict` / `gh:issue-implement` / `gh:issue-proceed` / `gh:discussion-convert` / `devx:pr-verify-live` 는 각자 바인딩한 `$TARGET_REPO` 를 명시 전달하도록 바뀌었고, `.github/workflows/project-board-sync.yml` 은 `${{ github.repository }}` 를 `--repo` 로 넘긴다. `claude/hooks/post-gh-pr-create.sh` 는 `GH_REPO` 를 export 하므로 우선순위 2번으로 이미 정확해 호출부를 건드리지 않았다. 잔여 gap: `shell-common/functions/gh_flow.sh` 는 repo 변수를 전혀 바인딩하지 않아 자동 탐지에 의존한다 — 별도 이슈 대상 (#1405)**
