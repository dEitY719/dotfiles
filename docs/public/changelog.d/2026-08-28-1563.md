- 변경: **head 를 전진시키는 세 스킬(`gh:pr-reply` / `gh:pr-resolve-conflict` / `gh:pr-resolve-outdated`)이 push 성공 직후 `review-passed` 라벨을 무효화한다** — `devx:pr-review-all` 이 붙이는 판정 라벨은 "이 head 커밋이 리뷰됐다"는 주장인데, 세 스킬 모두 새 커밋을 밀어 넣으면서 라벨을 그대로 둬서 아무도 읽지 않은 코드에 스테일 판정이 살아남았다(PR #1529 에서 `gh:pr-resolve-outdated` 와 `gh:pr-resolve-conflict` 로 두 번 재현). `gh:pr-reply` 만 `review-blocked` 도 떼는데, `ACCEPTED_COUNT > 0 && DECLINED_COUNT == 0` 일 때 — 제기된 블로커를 전부 반영했다는 증거를 가진 유일한 지점이기 때문이다. 리베이스 스킬 두 개는 그 증거가 없으므로 `review-blocked` 를 남긴다(안전한 방향). 어떤 스킬도 두 라벨을 **붙이지** 않는다 — 발급자는 `devx:pr-review-all` 하나뿐이다 (#1563)
- 변경: **`_gh_pr_drop_label <pr> <label> <repo> [host]` 공유 헬퍼를 `shell-common/functions/gh_pr_edit_safe.sh` 에 추가** — "이미 없음"을 멱등 성공으로 흡수하는 REST DELETE 래퍼 하나로, 세 스킬이 같은 관용구를 복사하지 않는다. 단 그 판단을 DELETE 의 에러 텍스트에서 읽지 않는다: GitHub 은 라벨 부재·없는 repo·없는 PR·잘못된 `GH_HOST` 를 모두 같은 `Not Found (HTTP 404)` 로 답하므로, 404 를 그대로 믿으면 오타 난 repo slug 로 호출한 쪽이 스테일 `review-passed` 를 지웠다고 착각한다. 그래서 DELETE 가 실패하면 같은 호스트로 이슈의 실제 라벨 목록을 GET 해 검증한다 — 라벨이 없으면 rc 0(무음), 아직 있으면 rc 1, GET 자체가 실패하면(상태 불명) rc 1 로 원래 stderr 를 그대로 노출한다. 라벨은 URL path segment 이므로 percent-encoding 후 경로에 넣는다(`/`·공백 포함 라벨이 경로를 위조하지 못하게). DELETE 는 classic-Projects GraphQL deprecation 경로를 타지 않으므로 `_gh_pr_edit_safe_label` 과 달리 `gh pr edit` 선시도 없이 REST 직행이다. 판정 라벨 무효화 규칙의 SSOT 는 이 파일 헤더 주석이고, 각 스킬의 reference 문서는 그리로 링크만 건다. 회귀 테스트 13건이 `tests/bats/functions/gh_pr_edit_safe.bats` 에 붙었다 (#1563)
