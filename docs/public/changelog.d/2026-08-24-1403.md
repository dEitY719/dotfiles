- 변경: **`gh:*` 스킬 6종(`gh:issue-read` / `gh:issue-create` / `gh:issue-implement` / `gh:commit` / `gh:pr` / `gh:issue-flow`)이 모든 `gh` 호출에 host 와 repo 를 명시하도록 계약이 바뀌었다 — `GH_HOST="$TARGET_HOST" gh ... --repo "$TARGET_REPO"`. 종전에는 remote URL 에서 `owner/repo` 만 뽑아 `--repo` 로 넘기고 host 는 지정하지 않았는데, `gh` 는 `--repo` 가 없으면 git 의 `origin` 이 아니라 자기 `gh repo set-default` 를 따르므로 github.com 과 GHES 두 곳에 동시에 로그인한 PC 에서 **에러 없이 조용히 다른 서버를 조회**했다(OPEN 인 이슈가 "존재하지 않음" 으로 보고된 사례). SSOT 프리미티브 `shell-common/functions/gh_host.sh` 에 `_gh_host_from_url()` 을 추가해 `_gh_parse_owner_repo_url()` 과 **같은 remote URL 한 개**에서 host 와 repo 를 함께 읽게 했다 — 기존 `_gh_resolve_host()`(setup-mode → host 매핑, #703/#718)는 remote URL 이 없을 때의 fallback 으로만 남는다. 두 함수를 분리한 이유는 사내 PC 에서 `origin`=GHES / `upstream`=pull-only github.com 이라 PC 기본 host 와 대상 remote 의 host 가 정당하게 어긋나기 때문이다(setup-mode 만 보고 `GH_HOST` 를 정하면 `upstream` 대상 작업이 새로 깨진다). 각 스킬은 Step 1 에서 `export GH_HOST` 하므로 `gh_project_status.sh` / `gh_pr_edit_safe.sh` / `gh_discussion.sh` 같이 내부적으로 `gh` 를 부르는 헬퍼도 같은 host 를 상속한다. 부수 수정: `gh:pr` 의 board-sync 가 `GH_REPO` 를 재해석할 때 쓰던 `gh repo view --json nameWithOwner`(= gh CLI 기본 repo, 같은 버그의 원천)를 `git remote get-url origin` + `_gh_parse_owner_repo_url` 로 교체했고, `gh:pr` metrics-helper 의 `--repo` 없는 `gh issue view` fallback 분기를 제거했다 (#1403)**
