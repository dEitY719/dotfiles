## 2026-08-21
- 변경: **Hermes Agent 가 `claude/skills/` 스킬 SSOT 의 5번째 entry-level 합성 대상이 됐다 (#1376). `scripts/setup-skills-ssot.sh` 가 이제 OpenCode·Codex·Gemini 에 이어 Hermes 에도 스킬을 연결한다 — `~/.hermes` 가 없으면 종전 OpenCode/Gemini 와 똑같이 경고만 남기고 건너뛰는 non-fatal 스킵이다. 다만 **Hermes 만 합성 위치가 다르다**: 다른 CLI 는 `skills/` 루트에 직접 entry symlink 를 깔지만 Hermes 는 전용 서브디렉토리 `~/.hermes/skills/dotfiles/<skill>` 안에서만 합성한다. `~/.hermes/skills/` 루트는 빈 디렉토리가 아니라 Hermes 자신이 능동적으로 관리하는 스킬 허브이기 때문이다 — `.hub/`(index-cache·audit.log·quarantine·taps.json), `.bundled_manifest`, `.curator_state`, `.usage.json*` 메타데이터와 `apple/` `github/` `productivity/` 같은 카테고리 네임스페이스가 이미 그 자리를 쓰고 있고, 백그라운드 curator 가 사용량을 추적해 stale 스킬을 자동 archive 한다. 루트에 직접 합성하면 그 네임스페이스와 충돌하므로 서브디렉토리로 격리했다. 합성 자체는 신규 헬퍼 없이 기존 `link_skills_compose` 를 대상 경로만 바꿔 재사용하므로 레거시 dir-symlink 마이그레이션·사용자 symlink 보존+경고·stale 정리·멱등성이 다른 CLI 와 완전히 동일하게 동작하고, Verify 섹션에도 `compose` 모드 검증이 추가됐다. Hermes 소유 경로를 절대 건드리지 않는다는 보장은 회귀 테스트로 고정했다 — 허브 메타데이터와 카테고리 디렉토리를 시딩한 뒤 스크립트를 돌려 파일 크기·mtime·권한이 전부 그대로이고 최상위에 새로 생긴 항목이 `dotfiles/` 하나뿐임을 확인한다. 겸사겸사 `claude/setup.sh` 의 위임 주석 2곳(single-account/multi-account)이 "Gemini / OpenCode" 로만 적혀 Codex 가 빠진 것처럼 보이던 문제를 "OpenCode / Codex / Gemini / Hermes" 로 정정했고, Antigravity CLI(`agy`) 가 OAuth 토큰을 `~/.gemini/antigravity-cli/` 에 두어 Gemini 런타임을 공유하는 덕에 별도 연동 분기 없이 `~/.gemini/skills` 합성을 그대로 상속한다는 사실을 `agy/AGENTS.md` ↔ `scripts/setup-skills-ssot.sh` 양방향 교차 참조로 문서화했다(종전에는 `agy/AGENTS.md` Non-Goals 한 곳에만 단독으로 적혀 있어 발견성이 없었다). Codex 전용 context-budget 가드(`scripts/maintenance/check_codex_skills_budget.py`)를 Gemini/agy/Hermes 로 확장할지도 함께 결론 냈다 — **확장하지 않는다**. 2% description 예산 트렁케이션은 Codex 로더 고유 동작이고 나머지 네 대상에서는 증상이 보고·재현된 적이 없어서, 관측되지 않은 한계를 `--target` 플래그로 미리 못박는 대신 그 판단 근거와 "언제 일반화해야 하는지"를 스크립트 docstring 에 남겼다. 기존 4개 CLI 연동 동작에는 변경이 없는 순수 추가다. **남은 수동 확인**: Hermes 의 스킬 탐색이 `skills/dotfiles/<skill>/` 깊이를 실제로 스캔하는지, curator 가 이 서브디렉토리를 archive/quarantine 대상으로 보지 않는지는 실제 허브에서 `hermes curator run --dry-run` 과 `.hub/audit.log` 로 확인해야 한다(NF-2 파일럿). 이상 동작 시 `rm -rf ~/.hermes/skills/dotfiles` 만으로 원본 SSOT 영향 없이 롤백된다**
- 변경: **`~/.hermes/config.yaml` 이 이 저장소로의 심링크가 아니라 첫 setup 때 한 번 복사되는 로컬 실파일이 됐다 — `hermes/setup.sh` Part 1 의 `_hermes_link_config` 를 `_hermes_ensure_config_copy` 로 교체했다. 계기는 추적 파일 `hermes/config.yaml` 이 한 PC 의 런타임 상태(`provider: nous`, `model.default`, `_config_version: 38`)로 덮여 문서용 주석이 통째로 사라진 사고다. 원인은 hermes CLI 자신이 그 경로를 다시 쓴다는 점(OAuth 설정, 모델 선택, `_config_version` 스탬프)이고, 이 쓰기는 시크릿 주입 직전에만 심링크를 떼던 `_hermes_materialize_config` 를 전혀 거치지 않아 그대로 저장소 파일에 착지했다. `claude/settings.json` 이 `/model` 로 겪은 write-through 누출(#924/#940)과 같은 실패 유형이며, 해법도 같다: 링크 대신 복사. 새 동작은 세 갈래다 — 파일이 없으면 템플릿을 복사하고, **레거시 심링크면 현재 해석된 내용을 그대로 실파일로 옮겨 detach 하며**(저장소 템플릿을 다시 복사하지 않으므로 그 PC 의 실제 hermes 설정이 보존된다), 이미 실파일이면 손대지 않는다. 마지막 갈래가 Claude 쪽 `cmp` 게이트 재동기화와 다른 점이 핵심이다: hermes 템플릿은 100% 주석이라 다시 전파할 값이 없고, hermes 는 `_config_version` 같은 키를 계속 다시 쓰므로 자동 재동기화는 CLI 와 싸우면서 사용자의 모델 선택만 날린다. 심링크가 사라져 Part 3 의 detach 단계도 불필요해졌으므로 `_hermes_materialize_config` 는 삭제했다. `shell-common/config/symlinks.conf` 의 hermes 항목도 제거했다 — 남겨두면 `symlink-manager init` 이 write-through 심링크를 그대로 되살린다(항목 자리에는 재추가 금지 사유를 주석으로 남겼다). 재발 방지로 golden rule 7 이 추가됐다: 추적 `hermes/config.yaml` 에 `_config_version:` 키가 있으면 실패한다 — 이 키는 hermes CLI 가 생성한 파일에만 찍히므로 존재 자체가 오염의 증거다. **기존 사용자 주의**: 다음 `./hermes/setup.sh` 실행이 심링크를 자동으로 실파일로 바꾸며 현재 내용은 보존된다. 이미 추적 파일이 오염됐다면 `git checkout hermes/config.yaml` 로 되돌리되, 반드시 setup.sh 를 먼저 실행해 로컬 사본을 만든 뒤에 되돌려야 라이브 설정을 잃지 않는다**

- 변경: **`hermes/setup.sh` Part 2(공식 CLI 설치)와 `hermes-help install`/`docs/guide/commands/hermes.md` 안내 문구가 설치 스크립트를 `sh` 대신 `bash` 로 파이프하도록 바뀌었다 — upstream `install.sh` 는 `#!/bin/bash` 셔뱅에 `[[ ]]`/배열 리터럴 같은 bashism 을 쓰는데, `curl ... | sh` 로 파이프하면 셔뱅이 무시되고 `/bin/sh` 가 실제로 가리키는 셸(Debian/Ubuntu 계열은 dash)이 스크립트를 해석한다. dash 는 `[[` 를 명령어로 오인해 계속 진행하다가 `local checks=(...)` 같은 배열 리터럴에서 파싱이 완전히 죽고(`Syntax error: "(" unexpected`), 그 시점에 파이프가 끊기며 `curl` 도 `Failure writing output to destination` 로 실패한다. `hermes/setup.sh` 안의 "sh 가 upstream 문서화 경로" 라던 주석도 실제로는 upstream 셔뱅과 어긋나 있어 함께 정정했다 (사용자 보고, 사내 PC WSL/Ubuntu 에서 재현)**
- 변경: **`gh:issue-implement` 의 `direct` 모드(기본값)가 superpowers 플러그인 설치 시 `superpowers:test-driven-development` 로 구현을 주도한다 — 종전에는 `plan`/`brainstorming` 모드만 superpowers 를 탔고, 기본값인 `direct` 는 항상 "통째 편집 → 전체 테스트 1회 → 최대 3회 caused/pre-existing 재시도 루프"라는 test-after 방식이었다. 이제 Step 2 의 기존 감지 로직(`superpowers-detection.md`)이 `test-driven-development` resolve 여부도 함께 확인해, 감지되면 이슈를 behavior 단위 red-green-refactor 사이클로 구현하고(반복 상한 없음, 같은 실패 반복 등으로 명백히 막혔다고 판단되면 사람에게 보고하고 멈춤), 미설치면 기존 3회 재시도 플로우로 폴백한다 — 두 경로 모두 완결된 흐름이며 폴백이 "저하된" 경로가 아니다. `constraints.md` 의 "pre-existing 실패는 절대 고치지 않는다" 하드 제약은 TDD 경로에도 그대로 적용되도록, TDD 스킬의 "Verify GREEN → 다른 테스트 실패 시 즉시 고쳐라" 지시에 대해 baseline 캡처로 얻은 `pre_existing_failures` 목록만 예외로 문서화했다(TDD 스킬 원문은 수정하지 않음). 최종 리포트에 어느 경로로 실행됐는지 보여주는 `Path: <tdd|fallback>` 필드가 추가됐다. `gh:issue-flow` 등 하위 소비자가 의존하는 `[step:gh-issue-implement/implement] OK` 마커·`--no-next-hint`·`IMPL_MIN` 타이밍은 변경 없음.**
